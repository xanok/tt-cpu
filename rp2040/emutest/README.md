# Replay test of the SPI RAM emulator in rp2040js

Checks the part between the chip and the demo board that the other tests do not reach: the emulator's PIO program and its service loop, with cpu8's pin order and timing.

```sh
make setup     # once: npm packages, bootrom, test firmware, trace tools
make test      # every halting example, both MISO_RISE strap settings
make sweep     # clock ratio x pad delay table
```

Needs Node.js, the OSS CAD Suite (Verilator), the ARM compiler and the pico-sdk, at the paths in the Makefile.

## How it works

1. **Record.** `trace` runs a program on the chip's Verilog (Verilator, with the ideal RAM model) and writes one line per chip clock: CS, SCK and MOSI, and for every clock edge where the chip samples a READ data bit, the value it must see on MISO. It also saves the memory at `HLT`.
2. **Emulate.** `replay.mjs` boots the `emu_test` firmware in rp2040js. That firmware is `emutest/main.c` plus the unmodified `spi-ram-emu/sram.c` and `sram.pio` of the real firmware. rp2040js has no second core, so the service loop that normally runs on core1 runs on core0.
3. **Replay and check.** The recorded pins are applied to the emulated GPIOs, with the CPU, both PIO blocks and the DMA stepped one system clock at a time. Every sampled MISO bit is compared, and at the end the emulated RAM is compared with the saved memory. Nothing outside the 4 KB may have been written.

Because every bit the chip samples is checked against what the ideal RAM gave it, a clean replay means the chip would have behaved exactly the same with the emulator as its RAM.

`emu_test_stock` is the same firmware with upstream's MISO timing (next bit right after the rising SCK edge), generated by CMake from `sram.pio`. It checks the fallback "stock timing with the strap at 1".

## Corrections to rp2040js

rp2040js 1.4.2 lacks three behaviours of the real PIO that the emulator depends on. `replay.mjs` adds them, following the RP2040 datasheet:

- A state machine whose enable bit is 0 does not run. rp2040js steps all of them.
- Changing the FIFO join bits flushes both FIFOs (this is how `pio_sm_clear_fifos()` works).
- A joined TX FIFO is 8 words deep.

Without the first two, every read after the first returns wrong data. They are gaps in the emulator, not in the firmware, but the result does rest on this reading of the datasheet.

## Results (2026-11-17)

`make test`: 20 examples x 2 strap settings, 40 of 40 pass at 20 system clocks per chip clock (200 MHz and 10 MHz). `ask.asm` is left out: it needs the firmware's mailbox feeder.

The four pairings, `hello.asm`:

| Emulator MISO timing | Strap 0 | Strap 1 |
|---|---|---|
| ours (after the falling edge) | pass | pass |
| upstream (after the rising edge) | fail | pass |

`make sweep` (`bubble_sort` and `factorial`): "ratio" is system clocks per chip clock, "delay" is the pad and multiplexer delay of the whole loop, chip to RP2040 and back.

| Pairing | Lowest ratio that works | Delay tolerated at ratio 20 |
|---|---|---|
| ours, strap 0 | 10 (fails at 8) | at least 35 clocks = 175 ns |
| ours, strap 1 | 10 (fails at 8) | 15 clocks = 75 ns (fails at 20) |
| upstream timing, strap 1 | 10 (fails at 8) | at least 35 clocks = 175 ns |

- The ratio limit is the re-arm time: after CS rises the emulator is ready again after about 80 system clocks, and the chip keeps CS high for 8 of its clocks. The firmware therefore limits the chip clock to sys/10.
- Strap 0 with our timing gives the RAM a full SCK period; strap 1 with our timing only half of one. Strap 0 is the right default.

## Limits

- rp2040js is a functional emulator. Its CPU cycle counts are approximate and it has no input synchronisers, so the timing figures are indicative, not sign-off numbers.
- The waveform is replayed, not fed back live. That is equivalent as long as every checked bit is right, which is what the test asserts.
- Only `sram.c` and `sram.pio` are exercised: not the USB loader, the clock generation or the output capture.
